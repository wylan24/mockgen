# mockgen compared with Prism, MSW and json-server

All four are good tools that solve overlapping problems in different ways. This page aims to help you pick the right one, including when that isn't mockgen. If something here is wrong or out of date, please [open an issue](https://github.com/wylan24/mockgen/issues/new/choose).

*Checked on 1 November 2026 against Prism 5.16.0, MSW 3.0.3 with `@mswjs/source` 0.7.0, json-server 1.0.0-beta.15 and mockgen 0.1.0-alpha.8, using each project's own README and docs. Sources are listed at the end.*

## In one line each

- **[Prism](https://github.com/stoplightio/prism)** is a mock server and validation proxy for OpenAPI 2, 3.0, 3.1 and Postman Collections, from Stoplight.
- **[MSW](https://mswjs.io)** intercepts requests inside your app, in the browser or in Node, with handlers you write in JavaScript or TypeScript.
- **[json-server](https://github.com/typicode/json-server)** is a full fake REST API from a single JSON file.
- **mockgen** is a mock server that generates realistic, deterministic data from an OpenAPI 3 spec or a folder of sample responses.

## At a glance

| | Prism | MSW | json-server | mockgen |
| --- | --- | --- | --- | --- |
| Defined by | OpenAPI 2 / 3.0 / 3.1, Postman Collections | Handlers in JS/TS. OpenAPI or HAR via `@mswjs/source` | A `db.json` file | OpenAPI 3.0 / 3.1, or a folder of sample JSON responses |
| Runs as | HTTP server (CLI) | Service worker in the browser, interceptor in Node. No server | HTTP server (CLI) | HTTP server (CLI, Docker), or in-process for tests |
| Response data | Spec examples by default, generated with `-d` (json-schema-faker, Faker via `x-faker`) | Whatever your handlers return | The contents of your JSON file | Generated by default, matched to field names. Spec examples when present |
| Same data every run | Not documented for dynamic mode | Up to your handlers | Yes, it's your file | Yes: seeded, and byte-identical across OS and Node versions |
| Validates requests against the spec | **Yes** (body, query, headers, path, security) | No | No | No |
| Validation proxy to a real API | **Yes** (`prism proxy`) | No (passthrough and bypass only) | No | No |
| Create, update, delete | Not documented (data persistence is on Prism's roadmap) | With `@msw/data`, in memory | **Yes** | Yes, with `--stateful`, in memory |
| Pagination | Not documented | In your handlers | **Yes**, plus filtering, sorting, relations (`_embed`) | Yes: page, offset and cursor styles, `Link` and `X-Total-Count` headers. No filtering or sorting |
| Choose a status per request | `Prefer: code=404` | In your handlers | No | `X-Mock-Status: 404` or `?__status=404` |
| Simulated latency | Not documented | `delay()` in handlers | Removed in v1 (use DevTools throttling) | `--delay`, `X-Mock-Delay`, or per route in the config |
| Config / overrides | `x-faker` in the spec, `Prefer` headers | It's all code | n/a | `mock.config.ts`: per-route status, body, merge, headers, delay |
| Hot reload | Yes | n/a | Not documented | Yes, and it keeps serving the last good version if the spec breaks |
| License | Apache-2.0 | MIT | MIT | MIT |
| Maturity | Stable (v5) | Stable (v3) | v1 is beta; v0.17 is the stable line | Alpha (0.x) |

## When to pick each

### Pick Prism when

- **You need request validation.** Prism checks requests against the spec and answers with the spec's 422 or 400, or a problem+json error, when a client sends something invalid. That catches client bugs that a mock which accepts anything won't. mockgen doesn't validate requests.
- **You want to check a real API against its spec.** `prism proxy` forwards traffic to the real server and reports where requests or responses break the contract. mockgen has no proxy.
- **Your spec is Swagger 2.0 or a Postman Collection.** mockgen needs OpenAPI 3.0 or 3.1. Convert older specs with [swagger2openapi](https://github.com/Mermade/oas-kit) first.
- **Your team already uses Stoplight.** Prism powers mocking in Stoplight's hosted platform.

Where mockgen differs: realistic data by default, rather than examples or `"string"`/`0` placeholders unless you turn on dynamic mode. Data is stable across runs, lists are consistent with their detail routes, paging works, and there's an optional stateful mode.

### Pick MSW when

- **You want mocks inside the app, with no server.** MSW intercepts `fetch` in the browser and requests in Node, so tests and Storybook stories run without starting anything, and the network tab shows real requests.
- **You want full control in code.** Every handler is your own JavaScript or TypeScript, so any logic is possible.
- **You're mocking APIs that have no spec.** Handlers don't need one.

Where mockgen differs: no handlers to write, because the spec is the mock. It's a real HTTP server, so anything can call it: a mobile app on a phone, `curl`, a backend in another language, or a teammate's machine. The two also combine well. `@mswjs/source` can generate MSW handlers from the same OpenAPI document, if you want interception and a spec.

### Pick json-server when

- **You have (or can write) the data you want, and no spec.** A `db.json` file is the whole setup.
- **You need filtering, sorting or relations.** `?views:gt=100`, `_sort=-views`, `_embed=comments` and dependent deletes are built in. mockgen pages through lists but doesn't filter or sort them.
- **You want full CRUD out of the box.** Writes are on by default.

Where mockgen differs: you don't write the data. It's generated from the spec or inferred from a few sample responses, at any size, and it always matches the API's real shape. mockgen also has per-request errors and latency, which json-server v1 removed.

### Pick mockgen when

- **You have an OpenAPI spec, or a few real responses, and want a working API now** with no handlers, no fixtures and no data to write.
- **Front-end or mobile work needs realistic, stable data:** names, emails and avatars that match each other, the same records on every reload, and lists that agree with their detail pages.
- **You're building the hard UI states:** errors, slow responses, empty lists and the last page, each on demand per request.
- **Tests need a predictable API:** seeded output is byte-identical everywhere, so snapshots don't flap.
- **The backend doesn't exist yet:** start from sample JSON, then graduate to a spec with `mockgen infer`.

And when not: if you need request validation or a contract-checking proxy, use Prism. To mock inside the app without a server, use MSW. For a quick CRUD API over data you already have, with rich querying, use json-server.
